# The AI-Era Spec Wave and the Nix Precedent

Terminology used throughout, matching the lips project vocabulary: **kernel** is the
self-describing spec-language itself; a **vocabulary** is a problem-specific language minted
in the kernel; a **Solution** is an application spec written in some vocabulary; the
**System** is kernel plus vocabularies plus compiler plus Nix realization.

This document surveys two bodies of prior art relevant to that architecture. Half 1 asks
whether any 2023-2026 "spec-driven development" tool actually makes a spec the deterministic
source of truth, or whether all of them are prompt engineering with approval gates. Half 2
asks what the NixOS module system gets right and wrong as a working example of "vocabulary
over one general substrate," since that pattern is the architectural bet lips rests on.

## Half 1: The AI-Era Spec-Driven Wave

### What "Spec-Driven Development" Means, and Why the Term Is Contested

Birgitta Böckeler's comparison of the three most-cited tools is the best available
firsthand account, because she actually used all three on real tasks rather than reading
their marketing copy. She proposes a three-level taxonomy that this survey adopts:
**spec-first** (a spec is written before code, then discarded or left stale), **spec-anchored**
(the spec is kept and used for future changes), and **spec-as-source** (the spec is the only
artifact a human edits; code is regenerated from it). Her finding: "All SDD approaches and
definitions I've found are spec-first, but not all strive to be spec-anchored or
spec-as-source" (Böckeler, "Understanding Spec-Driven-Development: Kiro, spec-kit, and Tessl,"
martinfowler.com, 15 October 2025,
<https://martinfowler.com/articles/exploring-gen-ai/sdd-3-tools.html>). This distinction maps
directly onto lips's own ambition: a Solution is meant to be spec-as-source from day one,
not an aspiration bolted on after the fact.

### Tool-by-Tool: Where the LLM Sits, and What Breaks There

**GitHub Spec Kit.** The spec artifact is a set of Markdown files generated by slash commands
(`/speckit.specify`, `/speckit.plan`, `/speckit.tasks`) into per-feature directories, governed
by a project-level `constitution.md` (source:
<https://github.com/github/spec-kit>, methodology doc
<https://raw.githubusercontent.com/github/spec-kit/main/spec-driven.md>). The actual
`spec-template.md` is prose with explicit `[NEEDS CLARIFICATION: ...]` markers the LLM must
insert instead of guessing
(<https://raw.githubusercontent.com/github/spec-kit/main/templates/spec-template.md>). The
determinism boundary is total: an LLM authors the spec, the plan, the tasks, and the final
code; the only non-LLM parts are deterministic scaffolding (branch creation, file
templating). "Gates" such as the Simplicity Gate or Anti-Abstraction Gate are checklists the
same LLM grades itself against; the methodology doc admits templates "act as sophisticated
prompts that constrain the LLM's output," not a checker external to the model
(spec-driven.md, section "Template-Driven Quality"). Böckeler confirms this in practice:
checklists are "interpreted by AI, so there is no 100% guarantee that they will be respected."

**AWS Kiro.** The spec is three Markdown files per feature: `requirements.md` (user stories
plus acceptance criteria in EARS notation), `design.md` (architecture, sequence diagrams), and
`tasks.md` (a dependency-graphed task list Kiro can execute in parallel "waves")
(<https://kiro.dev/docs/specs/>, <https://kiro.dev/docs/specs/feature-specs/>). EARS ("Easy
Approach to Requirements Syntax") constrains each requirement to the template `WHEN
[condition] THE SYSTEM SHALL [behavior]`, a real requirements-engineering formalism, but it is
still natural language interpreted by the model, not a grammar a compiler parses. The one
integrity check offered, "Analyze Requirements," is again an LLM judging another LLM's prose
for "logical inconsistencies, ambiguities, conflicting constraints, and gaps," not a
type-checker. Determinism boundary: identical to Spec Kit, an LLM at every phase; only the
task-dependency graph execution (which tasks run in which wave) is genuinely deterministic,
and that graph is itself derived by an LLM reading `tasks.md`.

**Tessl.** Of the three, Tessl aspires furthest toward spec-as-source: code carries a `//
GENERATED FROM SPEC - DO NOT EDIT` header, and `.spec.md` files use YAML frontmatter plus
inline `[@test]` links that tie a natural-language requirement to a concrete test file
(<https://github.com/tesslio/spec-driven-development-tile>,
<https://docs.tessl.io/use/spec-driven-development-with-tessl>). This is the closest any tool
gets to a real determinism boundary, because test execution after generation is genuinely
deterministic. But the tests themselves are usually LLM-authored from the same prose spec, so
passing tests confirms consistency with the model's own reading of the spec, not an
independent check against human intent. Böckeler ran the sharpest experiment here: generating
code from the same Tessl spec multiple times and observing different output each time. Her
conclusion is worth quoting directly because it is the central finding of this survey's first
half: "Even at this low abstraction level I have seen the non-determinism in action though,
when I generated code multiple times from the same spec." Spec-as-source, in the one tool
that tries hardest, does not remove non-determinism; it only narrows the surface over which
non-determinism operates (one file instead of a whole app).

**BMad Method.** A fourth widely-adopted entrant (50k+ GitHub stars,
<https://github.com/bmad-code-org/BMAD-METHOD>) generalizes the same pattern into a
multi-agent "agile" role play: a Product Manager agent, Architect agent, and Dev agent each
write and hand off Markdown artifacts (PRD, architecture doc, story files). The determinism
boundary is unchanged: more agent personas, still no compiler, still Markdown consumed and
produced by LLMs at every step.

### The Manifesto Behind the Wave: OpenAI's "Spec Is the New Code"

The most theoretically explicit argument for spec-as-primary-artifact comes not from a tool
but from a talk: Sean Grove of OpenAI's alignment team, "The New Code," AI Engineer conference
2025 (transcript: <https://lawwu.github.io/transcripts/8rABwKRsec4.html>). His argument: code
is "a lossy projection" of intent, comparable to a decompiled binary, and the real artifact of
value is the specification, exemplified by OpenAI's Model Spec, "a collection of Markdown
files" with per-clause IDs (e.g. `SY73`) that link to test-prompt files. He explicitly calls
this "executable": "you take your specification and a set of very challenging input prompts,
and you sample from the model under a test or training. You then take its response... and you
give that to a greater model. And you ask it to score the response according to the
specification." This is the cleanest illustration in the entire survey of the central
question's answer: "executable" here means graded by another LLM, not run by an interpreter.
Grove's own worked example, the GPT-4o sycophancy incident, is instructive precisely because
the mechanism that caught the regression was not a machine check; the Model Spec's "don't be
sycophantic" clause let humans debate whether shipped behavior conformed to written intent, a
social and editorial process, not a computational one. The talk is valuable to lips as a
philosophy statement (specs align humans, code is downstream) but it explicitly does not
claim, and does not achieve, deterministic execution.

### The Contrast Case: Context Files Are Not Specs

AGENTS.md (<https://agents.md/>, stewarded by the Agentic AI Foundation under the Linux
Foundation) and Cursor's `.cursor/rules` convention occupy a different category that Böckeler
usefully separates from "spec": a **memory bank**, project-wide context read on every agent
session, not scoped to one feature. AGENTS.md's own FAQ states the design bluntly: "Are there
required fields? No. AGENTS.md is just standard Markdown. Use any headings you like; the agent
simply parses the text you provide." There is no schema, no validation, no compiler; it is a
convention for where to put free text. This is useful for lips mainly as a negative
example: it shows the AI tooling ecosystem converging on unstructured natural-language context
even where a schema would cost little, which is the opposite of the kernel's bet on typed,
structured vocabularies.

### Real-Use Feedback and the Recurring Failure Mode

Two independent field reports converge on the same failure pattern, which answers this
survey's key question for Half 1.

Böckeler, after hands-on use of Spec Kit and Kiro on both a small bugfix and a mid-sized
feature: "spec-kit created a LOT of markdown files for me to review. They were repetitive...
Overall they were just very verbose and tedious to review... I'd rather review code than all
these markdown files." She also documents an LLM ignoring its own spec: a Spec Kit research
step correctly identified existing classes in the codebase, but "the agent ultimately ignored
the notes that these were descriptions of existing classes, it just took them as a new
specification and generated them all over again, creating duplicates." She names this "a
false sense of control": checklists and gates create the appearance of a controlled process
without a mechanism that actually enforces it.

François Zaninotto's independent critique, "Spec-Driven Development: The Waterfall Strikes
Back" (Marmelab, 12 November 2025,
<https://marmelab.com/blog/2025/11/12/spec-driven-development-waterfall-strikes-back.html>),
documents the same category of failure with a concrete, damning example: "the agent marked
the 'verify implementation' task as done without writing a single unit test, it wrote manual
testing instructions instead." His summary term for the pattern is "False Sense of Security":
"the SDD methodology is meant to keep the coding agent on track, but in practice, agents don't
always follow the spec." He also draws the same historical analogy Böckeler draws
independently (both reference Model-Driven Development, MDD, from the 1990s-2000s): heavy
upfront specification without a real compiler reproduces Big Design Up Front, at the cost of
reviewing prose instead of reviewing code, "spending 80% of your time reading instead of
thinking."

**Answer to the central question of Half 1.** None of the surveyed tools make the spec a
deterministic single source of truth in the sense lips intends. Every one of them runs an
LLM at spec-authoring time, plan time, task time, and code-generation time; the only
genuinely deterministic components are peripheral (file scaffolding, task-dependency
scheduling, test execution after the fact). Where a tool claims "executable" specs (Tessl,
the OpenAI Model Spec), execution cashes out as another LLM judging conformance, which is
non-deterministic and, per Böckeler's repeated-generation experiment, not even repeatable.
Structurally, every tool in this survey is prompt engineering with added ceremony:
approval gates, checklists, and file templates that shape what the LLM is likely to produce,
but nothing in the pipeline can refuse to compile a Solution that violates a rule the way a
type-checker refuses ill-typed code. This is the gap lips's compiler is meant to close:
move the boundary between human-authored intent and machine-checked realization to a point
where the "compile" step contains zero LLM inference, matching the Nix precedent surveyed
next.

## Half 2: The Nix Precedent

### How the Module System Works, Verified Firsthand

The NixOS module system is a plain Nix-language library (`lib.evalModules` in nixpkgs'
`lib/modules.nix`), not a separate language: "The module system is a Nix language library that
enables you to declare one attribute set using many separate Nix expressions, impose type
constraints on values in that attribute set, [and] define values for the same attribute in
different Nix expressions and merge these values automatically according to their type"
(nix.dev, "Module system,"
<https://nix.dev/tutorials/module-system/index.html>). A module is a function of the form
`{ config, lib, pkgs, ... }: { imports = [...]; options = { ... }; config = { ... }; }`
(NixOS manual, "Writing NixOS Modules," Example 14,
<https://nixos.org/manual/nixos/stable/#sec-writing-modules>). Options are declared with
`lib.mkOption { type = ...; default = ...; description = ...; }`; types compose (`types.int`,
`types.listOf types.str`, `types.submodule {...}`, etc.).

I verified the four load-bearing mechanics directly with `nix-instantiate --eval` (Nix
2.34.7) rather than trusting secondhand descriptions, since firsthand verification of a
mechanism this central is cheap and the module system's behavior under composition is exactly
what lips's own compiler needs to reproduce or improve on.

- **Priority-based override (`mkForce`, `mkDefault`, `mkOverride`).** Three modules setting
  `foo` to `1` (default), `42` (via `lib.mkForce`), and `7` (plain) resolve to `42`; `mkForce`
  is sugar for `mkOverride 50`, `mkDefault` for `mkOverride 1000` (lower number wins; verified:
  `lib.mkForce 1` evaluates to `{ _type = "override"; content = 1; priority = 50; }`,
  `lib.mkDefault 1` to `priority = 1000`).
- **Conflicting plain definitions are a hard error, not silent overwrite.** Two modules
  setting `foo = 7;` and `foo = 8;` with no priority annotation fail evaluation with: `The
  option 'foo' has conflicting definition values: - In '<unknown-file>': 8 - In
  '<unknown-file>': 7. Use 'lib.mkForce value' or 'lib.mkDefault value' to change the
  priority.` The `<unknown-file>` in my test is an artifact of using inline anonymous modules;
  in real usage the module system records the source file and line of every definition, which
  is precisely the location information that later shows up (or fails to show up) in
  user-facing error messages, see pain points below.
- **Fixpoint evaluation.** A module can define `derived = config.base * 2` while a different,
  later module defines `base = 21`; the result (`42`) confirms the module system evaluates
  `config` as a lazy fixpoint over the merged result of all modules, not a single left-to-right
  pass. This is what allows options to reference each other regardless of import order, and it
  is a genuinely powerful property: definitions are declarative facts contributed to one
  global fixpoint, not imperative statements executed in sequence.
- **Typo detection.** Assigning a value to an undeclared option name (`fooo` instead of `foo`)
  fails with `The option 'fooo' does not exist... Did you mean 'foo'?`. The module system does
  catch this by default via `evalModules`' built-in `check`, contrary to a common belief that
  it silently swallows typos. It does not catch it, by design, inside a `submodule` that
  declares a `freeformType`: "Since this feature nullifies name checking for entire option
  trees, it is only recommended for use in submodules" (NixOS manual, "Freeform modules,"
  same manual URL as above). Freeform types are the module system's escape hatch for
  attribute sets that should accept arbitrary keys (e.g. arbitrary systemd unit settings), and
  they are also where its type safety guarantee ends.
- **List merging (`mkMerge`, `mkBefore`).** Modules contributing to a `listOf str` option via
  plain assignment, `mkMerge [[...] [...]]`, and `mkBefore [...]` concatenate rather than
  override, in an order governed by priority and declaration order (verified: `[ "first" "vim"
  "curl" "git" ]` from four modules using `mkBefore`, `mkMerge`, and plain assignment
  respectively). This is the mechanism that lets, for example, every module contributing to
  `environment.systemPackages` add its own packages without knowing about any other module.

Warnings and assertions (`config.warnings`, `config.assertions`) are a convention layered on
top by NixOS's own modules (e.g. `nixos/modules/misc/assertions.nix`), not a primitive of
`evalModules` itself: "Although Nix has the abort and builtins.trace functions to perform such
tasks, they are not ideally suited for NixOS modules. Instead... you can declare your warnings
and assertions using the NixOS module system" (NixOS manual, "Warnings and Assertions," same
URL). Assertions are collected during evaluation and only checked at build time, which means a
Solution-equivalent invariant violation surfaces as a build failure with a message, not a type
error at authoring time; this is a real gap between "declared as data" and "checked early."

### The Module System as Evidence for "Vocabulary Over General Substrate"

The module system is the strongest existing precedent for the architectural claim lips
rests on. NixOS itself is not a general programming exercise; it is thousands of small,
problem-specific vocabularies (`services.nginx.*`, `boot.loader.*`, `networking.*`) each
minted as typed options on top of one general, lazy substrate, the Nix expression language.
Every vocabulary composes through the same fixpoint and priority mechanism regardless of who
wrote it or when, and the vocabulary's typed shape is not an afterthought: it is
mechanically derived into user-facing tooling. `search.nixos.org/options`
(<https://search.nixos.org/options>) and the generated "Configuration Options" appendix of the
NixOS manual are built directly from the same `options` declarations that drive evaluation;
Noogle (<https://noogle.dev/>) extends the same idea to the wider Nix function ecosystem,
indexing nixpkgs library functions by type signature. None of this documentation is
hand-maintained prose describing the system: it is compiled from the same declarations that
the compiler (the Nix evaluator) type-checks and merges. This is precisely the "derived
tooling" property lips wants: because a vocabulary's options are structured data, not
prose, discoverability (search, docs, editor completion) becomes a mechanical export of the
compiler's own understanding of the vocabulary, at zero incremental authoring cost. Nickel's
retrospective critique of this same design makes the point from the opposite direction: making
`mkOption` a *library convention* rather than a language primitive means "discoverable by e.g.
code editors and IDEs" only accidentally, through nixpkgs-specific tooling built after the
fact, not through the language itself (Nickel, `RATIONALE.md`,
<https://raw.githubusercontent.com/tweag/nickel/master/RATIONALE.md>, section "Nix vs
Nickel"). Lips's kernel should take the derived-tooling property as a hard requirement
from day one, not an ecosystem accident.

### Known Pain Points

**Error messages.** This is the most consistently reported weakness across both practitioner
forums and the tools built explicitly to fix it. My own conflicting-definition test above
produced a stack trace through five internal frames of `lib/modules.nix` before reaching a
human-readable message; a practitioner account on r/NixOS attributes this directly to the
module system's implementation strategy: "I think the main source of bad errors is the module
system, Nix itself doesn't directly understand it so traces become an incomprehensible mess
filled with irrelevant implementation details" (reddit.com/r/NixOS, "Sorry guys, I'm
learning," 14 September 2024). Because the module system is a library, not a language
feature, the Nix evaluator has no concept of "option," "module," or "priority"; every module
system error is, from the evaluator's point of view, a generic attribute-set or type error
surfacing through library internals. Pierre Zemb's long-form retrospective after three years
of daily use is blunt about the cumulative effect: "The learning curve is a mountain, and the
daily friction can be grating" (Pierre Zemb, "Three Years of Nix and NixOS: The Good, the Bad,
and the Ugly," 1 July 2025, <https://pierrezemb.fr/posts/nixos-good-bad-ugly/>).

**Learning curve, decomposed.** Richard Goulter's analysis usefully splits "Nix is hard" into
three independent difficulties, worth citing as a structure rather than an anecdote:
difficulty with the Nix language itself (laziness, partial application, unfamiliar syntax),
difficulty with the Nixpkgs codebase's accumulated conventions (`callPackage`, `override`,
`overrideAttrs` vs. package-set-specific variants like `overridePythonAttrs`), and difficulty
with how underlying software interacts with Nix's non-standard filesystem layout (no FHS
paths, so prebuilt binaries do not simply run) (Richard Goulter, "The Three Difficult Things
about Nix," 9 May 2024,
<https://rgoulter.com/blog/posts/programming/2024-05-09-the-three-difficult-things-about-nix.html>).
The lesson for lips: the second difficulty, accumulated library convention indistinguishable
from language feature, is largely self-inflicted by choosing to build the module system as a
library rather than a language primitive, and is the one most directly avoidable in a
from-scratch kernel design.

**Weak typing and discoverability of the option mechanism itself.** Nickel's rationale
document, written by people who use Nix daily and built a language specifically to address its
gaps, is the sharpest first-party critique available: "Nix lacks any native typing and
validation capabilities... The merge system of Nickel is also in part inspired from the NixOS
module system. The NixOS module system has similar concepts but is implemented fully as a Nix
library. The rationale behind the merge system of Nickel is to bring back merging into the
scope of the language itself, bringing uniformity and consistency, and potentially improving
performance and error messages... Data validation directly leverages metavalues and the
contract system, instead of user-defined patterns such as `mkOption` and the like" (same
RATIONALE.md URL as above, section "Nix vs Nickel"). This is the single most important piece
of prior art for lips's kernel design: the team best positioned to know exactly concluded
that the module system's ideas (typed merge, declarative composition) are right, but its
implementation as a bolted-on library rather than a language primitive is precisely what
produces bad error messages and poor tooling.

**Evaluation performance.** Nix's evaluator is a single-threaded tree-walking interpreter over
a call-by-need graph of thunks; large configurations (a full NixOS system closure, or
home-manager on top of it) can take seconds to tens of seconds to evaluate before any build
starts, and thunk-forcing is not itself parallelizable without care because thunks mutate in
place ("Parallel Nix evaluation," Determinate Systems, 27 June 2024,
<https://determinate.systems/blog/parallel-nix-eval/>). This has motivated a full alternative
evaluator implementation, Tvix, built by the TVL project specifically to decouple evaluation
from building and to explore faster execution strategies such as bytecode compilation ("Tvix:
We are rewriting Nix," <https://tvl.fyi/blog/rewriting-nix>). An IEEE-published study
specifically examines the interaction of NixOS's two defining properties, modularity and
laziness, as a case study in functional operating-system configuration (Modularity and Lazy
Evaluation in NixOS, IEEE Xplore, <https://ieeexplore.ieee.org/document/10991248>), evidence
that this pairing is recognized as academically interesting, not merely folklore. For
lips, whose compiler will also need to merge many small vocabulary-defined fragments into
one realized System, evaluation performance is a second-order concern relative to correctness
and error quality, but not a free one: an unbounded, uncontrolled laziness model is a known way
to trade predictable performance for expressiveness.

### Prior Art: Compiling Higher-Level Languages to Nix

Four projects target the Nix expression language or the module system as a compilation
backend, each teaching a different lesson.

**terranix** (<https://terranix.org/>) is the most directly relevant precedent, because it
reuses the NixOS module system verbatim and retargets it at a different realization: "terranix
is a Nix-based infrastructure-as-code tool that combines the providers of Terraform (or
OpenTofu) and the lazy, functional configuration of NixOS... generating Terraform JSON that can
then be applied using the same providers." Its own feature list states the point plainly:
"NixOS module system: Type-checked configuration with sensible defaults, overrides, and
reusable modules," applied not to systemd units but to Terraform resources. This is close to
an existence proof of lips's compilation strategy: the module system's typed-merge
machinery is generic enough to be lifted out of NixOS entirely and pointed at an unrelated
target format, with the same benefits (composability, typed defaults, per-environment
overrides via plain function arguments) it has for system configuration.

**Nickel** (<https://www.nickel-lang.org/>, rationale at
<https://raw.githubusercontent.com/tweag/nickel/master/RATIONALE.md>) began as an attempt to
extract Nix's good ideas into a new, standalone language rather than compile into Nix: "Nickel
was born as an attempt to fix a number of shortcomings of the Nix language, but has evolved as
an independent, standalone configuration language that can evaluate JSON, TOML and YAML"
(Tweag, "Announcing Nickel 1.0," 17 May 2023,
<https://www.tweag.io/blog/2023-05-17-nickel-1.0-release/>). Its RATIONALE.md is explicit that
error messages and editor tooling, not expressiveness, were the deciding design factor over
embedding a DSL in an existing typed host language such as Haskell: "The end result of Nickel
being a useful tool is, all in all, error messages... Being built-in, contract error reporting
has special support in the interpreter with access to source positions, the call stack, and so
on. This is much harder to replicate in a host language" (same RATIONALE.md, section "Error
messages"). Nickel is the two-framings case flagged in the brief: it is both "a language that
tried to fix Nix's weaknesses directly" (opt-in gradual typing, first-class contracts, merge
as a language primitive) and, originally, a candidate frontend that could target Nix among
other backends, before pivoting toward being a standalone JSON/YAML/TOML-class configuration
language in its own right.

**dhall-nix** (<https://github.com/dhall-lang/dhall-nix>, now folded into dhall-haskell) is the
starkest single-sentence statement of the typing gap: "This package targets people who wish
Nix had a type system." It compiles the fully statically-typed, non-Turing-complete Dhall
language into plain Nix expressions, trading Nix's flexibility for total type safety and
guaranteed termination on the Dhall side, at the cost of two languages and a translation step
in the toolchain.

**PureNix** (<https://github.com/purenix-org/purenix>) is a PureScript backend that compiles
to Nix, aimed at letting authors write "code that's tricky to write in an untyped language" in
"a fully-featured, strongly-typed language instead." Its own README is candid about the
limits: "PureNix is not a complete typed replacement for Nix," because many Nix and nixpkgs
constructs (laziness-dependent patterns, `builtins`-level side effects) resist being given
useful PureScript types. The honest limitation is itself a lesson: a general-purpose typed
host language compiling to Nix inherits Nix's own semantic quirks (laziness without built-in
memory or tail-call management) at the target end, even when the source language is fully
typed.

**garn** (<https://garn.io/>), by contrast, does not compile a new language to Nix; it exposes
a TypeScript API (`garn.go.mkGoProject({...})`) running under Deno that calls out to Nix
underneath to realize reproducible dev environments and CI checks. This is the "embed in an
existing general-purpose language" strategy Nickel's rationale explicitly argues against for
error-message and tooling reasons, included here as the boundary case: it is popular and
pragmatic, useful evidence that plenty of real users prefer a familiar host language over a
new DSL even when the new DSL would type-check better, which is a real adoption-cost
consideration for lips's own vocabulary-authoring UX.

## Synthesis: What Lips Should Copy, What It Must Fix, and What the AI Wave Implies

**Copy from the module system.** (1) Typed options as the vocabulary surface: every
Solution-level concept should be a declared, typed option, not a free-form document, exactly
as `services.foo.enable : bool` is not prose but a checked fact. (2) Declarative merge with
explicit priority as the composition mechanism across vocabularies and layers, matching
`mkForce`/`mkDefault`/`mkMerge`; this is what let terranix repoint the same machinery at
Terraform with no changes to the merge semantics, and it is the cleanest existing model for
letting multiple Solutions, or a Solution and site-local overrides, compose without one
silently clobbering another. (3) Lazy fixpoint evaluation so that declarations can reference
the final, merged configuration regardless of authoring order, verified above to work exactly
as advertised. (4) Options as a compiler-derived artifact, not hand-written documentation:
search, docs, and editor completion should fall out of the same typed declarations the
compiler checks, the way search.nixos.org and Noogle are generated from real option and
function signatures rather than curated separately.

**Must fix, learning from the module system's own critics.** (1) Make the option/merge/type
mechanism a primitive of the kernel language itself, not a library convention bolted onto a
general substrate; Nickel's own postmortem on Nix is unambiguous that this exact choice is why
Nix's error messages are bad and its options are only accidentally discoverable. (2) Preserve
source provenance through every compilation stage; my own reproduction of a module conflict
showed `<unknown-file>` the moment modules are constructed anonymously, and reddit/blog reports
converge that library-implemented errors surface interpreter internals instead of a location
in the user's own text. A kernel that treats "which line of which Solution produced this
value" as first-class data throughout compilation avoids this by construction. (3) Do not
allow an untyped escape hatch (Nix's `freeformType`, or `attrsOf` catch-alls) to silently
swallow every future typo the way `freeformType` explicitly disables the "did you mean"
mechanism; if an escape hatch is unavoidable for extensibility, its blast radius must be
visible in the type, not merely documented in prose. (4) Treat cross-cutting invariants
(NixOS's `assertions`/`warnings`) as language-level, checked as early as static analysis
allows, not merely collected during evaluation and surfaced only at build time.

**What the AI wave implies for lips's determinism bet.** The 2023-2026 spec-driven wave
shows a market that wants exactly what lips is building, a dense human artifact that is
the real source of truth, but has so far only produced tools where an LLM sits at every stage
of the pipeline: authoring the spec, planning from the spec, generating tasks, writing code,
and even grading conformance to the spec (OpenAI's own "greater model" scoring described by
Sean Grove). The practitioner record is consistent that this produces a "false sense of
security": checklists an LLM can silently fail to honor, code regenerated non-deterministically
from an unchanged spec, and a net increase in review burden because markdown review does not
replace code review, it adds to it. The Nix module system is proof that the alternative is not
